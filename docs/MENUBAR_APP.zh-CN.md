# compactlab 评估与 menu bar 应用设计（草案）

状态：草案，2026-11-23。应用还没写代码；§6 的前三项（Codex 解析与时间模型、空闲压缩建模、`verify` 误判）已在引擎里修完。数字来自本机真实日志（单人、单机、list price），不是基准。

## 0. 结论

- **效果是真的，但只在 Opus 主会话上站得住。** 10-29 把阈值改到 650k 后，Opus 主会话每千轮成本 −21%（80% 区间 −24%～−17%，已补上日志里没有的压缩请求费用）。同一时期 Claude Code 的空闲压缩也上线了；把两者分开后，回放认为阈值本身贡献 −6.5%～−15%，其余来自空闲压缩。
- **空闲压缩建议保持开启。** 按现在的 650k，关掉它每天 list price 多约 9%、耗时多约 4 分钟，压缩少 3 次。它在符合条件的空闲间隔里只有 36% 触发，与上下文大小无关，多半取决于应用开着、机器醒着。
- **工具的闭环没有转起来。** 18 天没跑过分析；`serve`、`schedule`、`apply`、lens mod 都没在用；阈值是手改的，新模型要手补。
- **能做成 menu bar 应用，也值得做，** 但价值要来自持续功能（活跃会话离压缩多远、缓存冷热、设置漂移、改后验证），不是给 CLI 套壳。
- **先改引擎再做应用。** 一次分析 2 分 39 秒、约 1 GB 内存，缓存 231 MB 单文件整写，旧缓存 257 MB 没清。这些不改，后台常驻会比它省下的东西更烦人。
- **Codex 的 bug 已修：** 原来算出每天多花 4826 分钟，根因是适配器漏掉了九成工具调用（`custom_tool_call`），再加上找回步长单位不一致；修完后该组找回时间从 134 小时降到 0.04 小时（§6.1）。

## 1. 现状评估

### 1.1 效果（真实日志）

`compactlab verify --applied-at 2026-10-29T21:05 --new 650k --old 967k`（修复后重跑）：

| 分组 | 前 / 后（会话 / 活跃天） | 每千轮成本 | 回放预测（前 / 后） | 每千轮阈值压缩 | 每千轮空闲压缩 | 阈值压缩点中位数 |
| --- | --- | --- | --- | --- | --- | --- |
| Opus 5.5 主会话 | 125/21 → 86/25 | **−21.0%**（−24～−17） | −6.5% / −15.3% | 0.47 → 1.68 | 0.04 → 1.73 | 618k ✓ |
| Sonnet 5.5 主会话 | 41/19 → 22/15 | −38.8% | −3.8% / −4.0% | 0.49 → 0.29 | 0 → 2.86 | 617k ✓ |
| Sonnet subagent | — | +51% | 0% | 0 | — | 结论：阈值没碰到，与设置无关 |

怎么读：

- Opus 主会话是大头（按默认阈值回放约 $14k list price，占 Claude 总量八成），结果可信：改后已有 86 个会话、25 个活跃天，阈值压缩点就在 650k 附近。
- 之前“压缩次数是预测的 2～3 倍”，多出来的就是空闲压缩：分开计数后，阈值压缩和预测接近，空闲压缩单独一行。
- Sonnet 主会话：10-29 当天改过好几次（400k → 450k → 625k → 650k），起点时间不对，`verify` 会直接提示改用更早的时间。之前“压缩点 327k、可能被覆盖”的警告是空闲压缩造成的误报，已消除。
- subagent 两侧都不压缩，现在给出“阈值没碰到，成本变化来自工作内容”，不再说“省得比预测少”。

修复后的 `simulate --since-days 30`（balanced）：Opus 主会话选出 550k，比现在的 650k 每天省约 $12.5（成本 −5%），但把时间折成钱后综合得分只好约 1%，在 2% 容差内，结论是“保持当前”；Sonnet 主会话“无需调整”（空闲压缩开着时，它的会话从来到不了默认阈值）；Fable 5.2 原来按 Fable 5 的价格算（缓存读贵 5 倍），改按自己的价格后均衡方案是 750k，比你现在的 650k 还略差（成本 +4%），现在同样给出“保持当前”。之前的 450k / 475k 建议偏激进，原因正是没算空闲压缩。

Codex 从没设过阈值。修复后（GPT-6 原来全按兜底价 $3/$15 算，现按各自价格，含 272k 以上的长上下文加价）`gpt-6.1-sol` 主会话 balanced 仍是 175k、成本 −48%、每天省 64 分钟；省时这么多来自“上下文越小单轮越快”的拟合，只有一个用户的数据，建议先小步试（例如 300k）再用 `verify` 看。

### 1.4 工程质量

约 9.1k 行 Python，约 200 个测试，CI 绿，零运行时依赖，方法、安全、威胁模型文档齐全。`apply` 是唯一写配置的代码，有备份、manifest、按键回滚，应用要保持这个边界。弱点集中在后台场景：缓存设计（已修，见 §5 Phase 0 第 3 项）、跨进程单飞（`Calibrator` 的锁只在进程内；已修，见 §5 Phase 0 第 5 项）、结果文件按“最后一次运行”整体覆盖，以及时间模型对异常输入没有合理性检查。

## 3. 用法定义

### 3.1 目标用户与场景

重度 Claude Code / Codex 用户，Mac 上同时开多个会话。

| 场景 | 现在 | 有应用之后 |
| --- | --- | --- |
| 这个会话快压缩了吗 | 只有装了 lens mod 的 Claude Code 会话能看 | 菜单栏看所有活跃会话（Claude Code + Codex）离阈值多远 |
| 离开一小时回来 | 不知道缓存已冷，下一句会重写整段上下文 | “已冷：下次发送重写 480k，可先 /compact”，带复制按钮 |
| 阈值该不该调 | 记得才跑 `simulate`，再手改 | 每天后台重算；收益够大且连续两次方向一致才提醒；看 diff，一键应用 |
| 新模型上线 | 手动补 `modelSettings` | 日志出现没设置的模型就提醒，给出借用相近模型的值 |
| 改完有没有用 | 记得才跑 `verify` | 样本够了自动出结论卡片 |
| 设置被覆盖 | 不知道 | 压缩点持续不在设定值附近时提醒可能被 env、项目文件或 CLI 参数覆盖 |

### 3.2 菜单栏图标

- 一个小半圆刻度。默认只有图标；可选在旁边显示“上下文占比最高的活跃会话”的百分比（如 `72%`）。
- 状态：空闲（灰）、有活跃会话（常规）、某会话超过阈值 85%（琥珀）、有待办（小圆点：建议、漂移、验证结论）、引擎出错（感叹号）。
- 没有活跃会话、没有待办时保持安静，不闪、不动画。

### 3.4 设置窗口

| 页 | 内容 |
| --- | --- |
| 通用 | 登录时启动；菜单栏显示（仅图标 / 百分比）；语言（跟随系统 / 中 / 英） |
| 数据源 | Claude Code、Codex、dsh 开关与路径（默认自动发现，展示 `doctor` 结果） |
| 档位 | cost / balanced / time，时间价值，最小窗口，等待上限 |
| 自动调整 | 关（默认）/ 先问我 / 自动（在同意范围内）；文件、模型、单步上限、冷却期，对应现有 `consent` |
| 通知 | 每类单独开关；勿扰时段 |
| 隐私 | 缓存位置与大小、清除缓存、不显示项目名 |
| 引擎 | 引擎路径与版本、最近日志、“复制诊断信息”（不含会话内容） |
| 关于 | 版本、检查更新 |

### 3.5 通知（全部限频，默认只开前三类）

1. 有值得应用的建议：收益 ≥ 2%/天 或 ≥ 2 分钟/天，且连续两次校准方向一致。动作：查看 / 稍后。
2. 漂移：日志里有没设置的模型；压缩点持续偏离设定值；设置被别人改了。
3. 验证结论出来了。
4. 引擎连续 3 次失败。
5. （默认关）某会话缓存已冷且上下文超过 X。

不做：每次压缩都通知；任何联网功能；遥测。

### 3.6 自动调整三档

| 档 | 行为 |
| --- | --- |
| 关（默认） | 只提醒，不写 |
| 先问我 | 提醒 → 审阅页 → 用户点“应用”才写；写前校验文件没变、计划和看到的一致 |
| 自动 | 沿用现有 auto-apply 规则：同意范围、单步 ≤ 100k、冷却 7 天、不覆盖别人改过的值；每次写都发通知，带“撤销” |

## 4. 架构

### 4.1 方案比较

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| **A. Swift 原生应用 + 外部 Python 引擎，一次性子进程 + JSON 契约（推荐）** | 解析、价格、回放只有 Python 一份；引擎崩了应用不受影响；重分析跑完就退出，内存还给系统；没有端口和 token | 用户要先装引擎；要处理版本不匹配 |
| B. 应用连现有 `compactlab serve`（localhost HTTP） | 现成，调研子代理也推荐 | 分析在常驻进程里跑，CPython 很少把释放的堆还给系统，峰值内存大概率一直占着（待实测）；多一层端口、token、Host 校验 |
| C. 用 Swift 重写引擎（CodexBar 的做法） | 单语言、最轻、零安装 | 9k 行逻辑和 200 个测试要重写，两份实现会漂移；compactlab 的核心是回放模型，不是简单的用量统计 |
| D. 把 python-build-standalone 打进 .app | 零安装 | 每个嵌套 Mach-O 都要由内到外签名；同类应用里没人这么做；体积和更新成本高。留作 Phase 3 可选项 |

`serve` 继续保留，给只用 CLI、或想让别的工具读 JSON 的人用；应用内部不依赖它。

### 4.2 组成

```
compactlab.app（LSUIElement，无 Dock 图标）
├─ SwiftUI：MenuBarExtra(.window)、Settings、UserNotifications、SMAppService 登录项
├─ EngineSupervisor：发现引擎、握手、调度、超时、取消、退避重启、低优先级
├─ FSEvents：~/.claude/projects、~/.codex/sessions（2 s 去抖）
└─ 不解析 JSONL、不写 settings、不联网
外部引擎：compactlab（uv tool / Homebrew formula 安装）
```

引擎发现顺序：设置里手填的路径 → `PATH` → `~/.local/bin` → `/opt/homebrew/bin` → `uv tool dir`。启动时执行 `compactlab engine hello` 握手，版本不兼容就进入“引擎过旧”状态：只读功能照常，写操作停用，并给出升级命令。

两类引擎调用：

| 调用 | 形态 | 频率 | 内存目标 |
| --- | --- | --- | --- |
| `compactlab engine watch` | 常驻、轻量；只读活跃文件尾部，输出 JSON Lines：会话上下文、模型、生效阈值、最后活动时间、缓存何时变冷 | FSEvents 触发（stdin 发 `refresh`），活跃时最多每 5 s 一次 | < 40 MB（实测峰值 32 MB） |
| `compactlab engine calibrate / result`（已有）；`verify / plan / apply / revert`（Phase 0 第 5 项和 Phase 2） | 一次性子进程，跑完退出 | 定时（默认每天）+ 手动 | 峰值 < 300 MB（已达到：追加日志后约 200 MB，没有变化时 56 MB） |

- 活跃会话放在 Python 里做，是为了让格式知识（resume 复制的历史、fork、subagent 目录、Codex token_count）只有一份。如果 watch 进程的常驻开销实测不达标，退路是只把“读最后一条 usage”这一小段移到 Swift，并用同一套夹具测试。
- 契约：每个输出带 `engine_api` 版本；Python 测试和 Swift 测试共用一套 JSON 夹具（`tests/contract/`）。字段和命令见 [ENGINE_API.md](ENGINE_API.md)。
- 写配置只走 `engine apply`，并带 `--expect-plan <hash>`：引擎重算的计划和用户在审阅页看到的不一致就拒绝写。
- 跨进程单飞：`~/.compactlab/service/lock`（`flock`）。应用、CLI、launchd 定时任务，谁拿到锁谁跑。
- URL scheme 只用于“打开报告 / 打开某页”，不接受任何写操作。

### 4.3 分发与系统集成

- macOS 14+，Swift 6 严格并发；`MenuBarExtra` `.window` 样式，Observation。
- 登录项用 `SMAppService.mainApp`，不另装 LaunchAgent。现有 `compactlab schedule` 留给只用 CLI 的人，两者靠文件锁互斥。
- 不开 App Sandbox（要读 `~/.claude`、`~/.codex`，按同意写 settings），用 Developer ID 签名、Hardened Runtime、公证。
- 发布：DMG + Homebrew cask（`depends_on formula: "compactlab"`，引擎走 formula 安装）+ Sparkle 2（EdDSA）。
- 学 CodexBar：设置里放“安装 CLI”按钮；CI 里做打包后启动冒烟测试（假 HOME、夹具日志）；主线程卡顿看门狗。

### 4.4 稳定性要求

| 项 | 要求 |
| --- | --- |
| 资源 | 应用常驻 < 60 MB；watch < 40 MB；空闲 CPU ≈ 0（不轮询，只靠 FSEvents 和定时器） |
| 电源 | 低电量模式、或用电池且电量 < 20% 时推迟定时重算 |
| 睡眠唤醒 | 唤醒后重排定时器；错过的校准只补一次 |
| 失败 | calibrate 超时 10 分钟；可取消；沿用 5 分钟起翻倍的退避；watch 崩溃自动重启，1 分钟内 3 次就停下并提示 |
| 数据 | 日志目录不存在、没权限、文件截断或轮转、引擎输出乱码，都要有明确状态，不崩 |
| 日志 | 应用用 `os.Logger`；引擎写现有轮转日志；“复制诊断信息”一键导出 |
| 测试 | Python 现有测试 + 契约夹具；Swift 侧 ViewModel 单测（喂夹具）、Supervisor 单测（假引擎：超时、崩溃、乱码）；发布前在真实 11 GB 日志上冒烟 |

## 6. 其他优化建议（不做应用也值得做）

按优先级：

1. ~~**Codex 时间模型爆掉。**~~ 已修。根因有三层：适配器不认 `custom_tool_call`/`custom_tool_call_output`（30 天 24,107 次 `exec`），只数到 `{"accepted":true}` 这类小回执；Codex 先写工具输出再写 `token_count`，原来的延迟口径要么是工具运行时间要么是 0；找回时间用“全部工具结果的中位数”去除先验的找回 token，单位不一致。另外加了“收益不超过 2% 容差就保持默认”的规则（和选点规则一致）。
2. ~~**空闲压缩建模。**~~ 已完成：识别、回放（摘要读取与输出计费、回来时更小的上下文、找回成本、没回来的会话白做的摘要）、开/关两种状态的全局建议、`recommend` 片段、`verify` 分开计数。
3. ~~**`verify` 误导结论。**~~ 已修：阈值没碰到时给出 `untouched`；成本里补上日志不记的压缩请求。
4. ~~**缓存。**~~ 已修（Phase 0 第 3 项）：原来 1 GB 峰值、231 MB 单文件整写，旧版 257 MB 没删，`cache clear` 只删当前版本，缓存里有转写片段。现在每个日志一行、增量写入，旧版本自动删除，`cache clear` 删所有版本，缓存里没有对话原文。
5. **`lens.json` 被单 harness 的运行覆盖。** 现状就是只剩 dsh。改成按 harness 合并。
6. **新模型没有阈值、没有价格。** 已做：模型 ID 按厂商和平台归一（Bedrock / Vertex / OpenRouter / Azure），没有价格时借同族最接近的型号并标注，`pricing auto on` 后后台在出现新模型时自动下载公开价格；`simulate` 列出借用价格的模型，以及没有单独设置、会话又到得了阈值的 Claude Code 模型（数据不足 3 天时给出参照值）。
7. **发布卫生。** PR #5 已绿 3 周没合；Dependabot 两个；v0.1.0 没打；没有 PyPI 和 Homebrew。应用要依赖可安装的引擎，这一步是前置。
8. **测准 recall。** lite 模式的 recall 是假设曲线，仍是可信度最大的缺口。在真实会话样本上跑一次 deep 模式，结果好坏都发布。
9. **订阅用户的口径。** 本机 100% 是 1 小时缓存，大概率是订阅；美元只是尺子。能读到额度窗口时（例如本机装了 CodexBar，读它的 CLI JSON），把影响折算成 5 小时 / 7 天额度的占比，而不是自己再做一遍用量统计。
